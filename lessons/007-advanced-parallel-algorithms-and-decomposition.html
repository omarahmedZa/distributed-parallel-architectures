Module 3 – Advanced Parallel Processing and Optimization

Lecture 7 — Advanced Parallel Algorithms and Decomposition Techniques

Apply domain and task decomposition strategies and analyze parallel algorithms for sorting, graph processing, and matrix operations, including their communication, load, and scalability trade-offs.

Why this matters

Parallel performance is as much about algorithm structure and decomposition as about hardware. Good decomposition exposes concurrency, balances load, and controls communication—poor choices negate architectural advantages.

Prerequisites: Fundamentals (models, speedup), Lecture 3, Lecture 5.

Learning objectives

  • Distinguish domain and task decomposition and select appropriate strategies.
  • Explain representative parallel sorting, graph processing, and matrix operation approaches.
  • Analyze data dependencies, communication patterns, and load balance implications.
  • Identify scalability limits and research challenges in parallel algorithms.

Core ideas and mechanisms

Decomposition techniques

Domain (data) decomposition partitions data across workers (e.g. array blocks, mesh subdomains, graph partitions) with each performing similar operations—natural for SIMD/SIMT and many scientific codes. Task decomposition partitions distinct computations/activities, possibly with different functions and dependencies—natural for pipelines, irregular workflows, or heterogeneous tasks. Hybrid decompositions combine both.

  • Granularity: fine-grained tasks expose parallelism but increase overhead; coarse-grained reduce overhead but risk imbalance/limited parallelism.
  • Dependencies: dictate synchronization/communication (halo exchanges, reductions, task graphs).

Parallel sorting

Parallel sorting algorithms trade comparisons, data movement, and communication. Examples include bitonic sort (regular compare-exchange network, good for fixed-size/pipeline implementations), sample sort (partition by sampled splitters, efficient for distributed memory with good load balance), and parallel merge/quick-sort variants. Key issues: global redistribution cost, load balance of partitions, and communication volume/latency.

Graph processing

Graphs often exhibit irregular structure, poor locality, and data-dependent communication. Parallel approaches include vertex-/edge-centric models (e.g. Bulk Synchronous Parallel style iterations with message passing) and partitioning to minimize edge cuts while balancing vertices/edges. Challenges: load imbalance from skewed degrees, synchronization per iteration, and high communication-to-computation ratios.

Parallel matrix operations

Dense linear algebra (e.g. matrix multiply, factorization) maps well to block decompositions with regular communication (e.g. 2D block/cyclic layouts, Cannon’s/SUMMA-style algorithms for multiplication). Sparse operations are more irregular and memory/communication bound. Efficiency depends on tiling for cache/locality, minimizing communication, and balancing work.

Worked example: block matrix multiply communication intuition

Multiplying two N×N matrices with 2D block decomposition distributes submatrices across processes. Each process computes local block products but must receive needed blocks of A/B from others (algorithm-dependent). As N grows, computation scales as O(N^3/p) while communication scales more slowly in well-designed algorithms, improving the communication-to-computation ratio for sufficiently large problems—an instance of scaling behavior analyzed in Lecture 9.

Limitations and scalability

  • Irregular workloads (e.g. power-law graphs) cause load imbalance and unpredictable communication.
  • Global synchronization and all-to-all style exchanges can bottleneck at scale.
  • Memory bandwidth and locality often limit sparse/graph kernels more than peak FLOPs.

Research problems

  • Communication-avoiding and synchronization-reducing algorithms.
  • Scalable dynamic partitioning/load balancing for irregular data (see Lecture 8).
  • Architecture-aware algorithm design for heterogeneous and deep memory hierarchies.

Recap and check for understanding

  1. When is domain decomposition usually preferable to task decomposition?
    Show answer

    When the same (or similar) operations apply over partitions of a large data set with regular structure, enabling balanced, data-parallel execution and locality-aware mapping.

  2. Why are parallel graph algorithms often harder to scale than dense matrix operations?
    Show answer

    Graphs are frequently irregular with skewed degrees and poor locality, leading to load imbalance, fine-grained communication, and synchronization overheads.

Research Activities

Literature review — Paper 1

Citation L. G. Valiant, “A Bridging Model for Parallel Computation,” Communications of the ACM, vol. 33, no. 8, pp. 103–111, Aug. 1990. DOI: 10.1145/79173.79181.

Core contribution: Proposes the Bulk Synchronous Parallel (BSP) model as a bridging abstraction for designing and analyzing portable parallel algorithms.

Method/architecture: Models computation as supersteps of local computation, communication, and barrier synchronization with parameters for processor speed, communication cost, and synchronization.

Key results: Provides a principled way to reason about algorithm performance across architectures and to structure communication/synchronization explicitly.

Limitations: Global synchronization per superstep can be restrictive for irregular/asynchronous workloads; real systems may benefit from more flexible execution models.

Literature review — Paper 2

Citation G. Malewicz, M. H. Austern, A. J. C. Bik, J. C. Dehnert, I. Horn, N. Leiser, and G. Czajkowski, “Pregel: A System for Large-Scale Graph Processing,” in Proc. ACM SIGMOD, 2010, pp. 135–146. DOI: 10.1145/1807167.1807184.

Core contribution: Introduces a vertex-centric, BSP-inspired programming model and system for scalable distributed graph processing.

Method/architecture: Computation proceeds in supersteps where vertices process messages, update state, and send messages; the system handles distribution, messaging, and fault tolerance.

Key results: Demonstrates practical scalability for large graphs by expressing algorithms in a simple iterative message-passing abstraction.

Limitations: Synchronous supersteps and message overhead can be inefficient for some algorithms; skewed graphs cause load imbalance, motivating asynchronous and optimized frameworks in later work.

Case study — ScaLAPACK for distributed dense linear algebra

What it is: ScaLAPACK (Scalable Linear Algebra PACKage) is a library of high-performance linear algebra routines for distributed-memory parallel computers.

Architectural design: Uses block-cyclic data distributions and coordinated parallel algorithms (built on BLAS/PBLAS/BLACS/MPI) to balance load and manage communication for dense matrix operations.

How it addresses lecture challenges: Applies structured domain decomposition and communication-aware algorithms to achieve scalability and portability across cluster/supercomputer architectures.

Observed strengths/limitations: Widely used for scalable dense linear algebra with good performance on suitable problem sizes; performance depends on matrix size, block sizes, process grids, and network characteristics, and dense-focused designs do not directly address irregular/sparse workloads.
