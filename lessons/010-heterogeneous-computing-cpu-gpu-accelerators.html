Module 4 – Heterogeneous and Emerging Architectures

Lecture 10 — Heterogeneous Computing Architectures: CPU, GPU and Accelerators

Analyze CPU–GPU and accelerator-based architectures, heterogeneous memory systems, and hybrid parallel designs, and evaluate their performance, scalability, and programmability trade-offs.

Why this matters

Modern high-performance systems increasingly combine general-purpose CPUs with GPUs and specialized accelerators to deliver throughput and energy efficiency. Exploiting heterogeneity requires understanding architectural differences, data movement, and mapping workloads to the right execution resources.

Prerequisites: Lecture 1, Lecture 2, Fundamentals (memory models, parallelism).

Learning objectives

  • Compare CPU and GPU/accelerator architectural characteristics and execution models.
  • Explain heterogeneous memory hierarchies and data movement implications.
  • Describe GPU clusters and hybrid parallel architectures.
  • Assess design decisions, limitations, scalability, and research directions in heterogeneous computing.

Core ideas and mechanisms

CPU–GPU architectures

CPUs optimize latency: few complex cores, deep caches, branch prediction, and out-of-order execution for diverse/irregular control flow. GPUs optimize throughput: many simpler cores organized into streaming multiprocessors/compute units executing large numbers of threads in SIMD/SIMT fashion, hiding memory latency with massive multithreading. Heterogeneous nodes couple CPUs (host/orchestration, serial/latency-critical code) with GPUs (data-parallel kernels) over interconnects such as PCIe or NVLink-class links.

Heterogeneous memory

Heterogeneous systems feature distinct memory spaces and characteristics: host DRAM, device high-bandwidth memory (HBM/GDDR), caches, and sometimes unified/managed memory abstractions. Performance depends on minimizing transfers, exploiting bandwidth where data resides, and managing coherence/unified addressing semantics when supported.

  • Explicit transfers: programmer/runtime copies data between host and device; high control, higher programming burden.
  • Unified/managed memory: simplifies programming but may incur migration/page-fault overheads if locality is poor.

GPU clusters and hybrid parallel architectures

GPU clusters scale by connecting many GPU-accelerated nodes via high-performance networks (Lecture 3), combining distributed-memory parallelism (e.g. MPI across nodes) with intra-node accelerator parallelism (CUDA/HIP/OpenCL/SYCL kernels). Hybrid parallel architectures may include multiple accelerator types (GPUs, FPGAs, AI accelerators) and require multi-level parallelism: across nodes, across devices, and within devices.

Accelerator-based and hybrid programming

Exploiting accelerators requires partitioning applications: offload suitable kernels, batch/stream work to amortize overheads, and overlap transfers with computation. Hybrid models (MPI + accelerator kernels, task graphs) coordinate across hierarchy levels while managing separate memory spaces and synchronization.

Limitations and scalability

  • Data movement bottlenecks: PCIe/interconnect bandwidth and latency can limit speedups (Amdahl/Gustafson effects at kernel level).
  • Memory capacity and locality: device memory limits and access patterns affect feasibility/performance.
  • Programmability/portability: multiple programming models and vendor ecosystems increase complexity.
  • Scaling GPU clusters: network contention, collective communication, and load imbalance constrain multi-node efficiency (Lectures 3, 5, 9).

Research problems

  • Unified/efficient heterogeneous memory and coherence across devices.
  • Portable, productive programming models and compilers for diverse accelerators.
  • Runtime scheduling, data placement, and overlap across heterogeneous resources.
  • Domain-specific architectures and co-design for emerging workloads (AI, data analytics).

Recap and check for understanding

  1. Why might offloading a small kernel to a GPU reduce overall performance?
    Show answer

    Data transfer and kernel launch overheads can exceed the compute savings if the kernel has little work or cannot amortize movement/launch costs.

  2. What is a key advantage of hybrid CPU–GPU architectures?
    Show answer

    They map latency-sensitive/irregular tasks to CPUs and throughput-oriented parallel kernels to GPUs/accelerators, leveraging complementary strengths.

Research Activities

Literature review — Paper 1

Citation J. Nickolls and W. J. Dally, “The GPU Computing Era,” IEEE Micro, vol. 30, no. 2, pp. 56–69, Mar./Apr. 2010. DOI: 10.1109/MM.2010.41.

Core contribution: Describes the architectural evolution of GPUs into programmable throughput-oriented processors suitable for general-purpose parallel computing.

Method/architecture: Explains GPU design principles (many-thread/SIMT execution, memory hierarchy, scalability) and contrasts them with latency-oriented CPU designs.

Key results: Articulates why GPUs deliver high throughput and efficiency for data-parallel workloads and how programming models expose this parallelism.

Limitations: High-level perspective; practical performance depends on memory behavior, divergence, and data movement, and the ecosystem has evolved significantly since publication.

Literature review — Paper 2

Citation E. Lindholm, J. Nickolls, S. Oberman, and J. Montrym, “NVIDIA Tesla: A Unified Graphics and Computing Architecture,” IEEE Micro, vol. 28, no. 2, pp. 39–55, Mar./Apr. 2008. DOI: 10.1109/MM.2008.31.

Core contribution: Presents the Tesla unified architecture that supports both graphics and general-purpose parallel computing on a common GPU platform.

Method/architecture: Details a scalable array of streaming multiprocessors, SIMT execution, and memory hierarchy enabling programmable parallel kernels.

Key results: Demonstrates an architectural foundation for GPU computing, enabling broader classes of data-parallel applications beyond graphics.

Limitations: Represents an early unified GPU computing design; subsequent generations changed capacities, memory systems, and interconnects, and programming/optimization challenges remain workload-dependent.

Case study — Frontier (ORNL) heterogeneous exascale system

What it is: Frontier is a leadership-class heterogeneous supercomputer at Oak Ridge National Laboratory, coupling AMD CPUs and GPUs at exascale to run large scientific workloads.

Architectural design: GPU-accelerated nodes connected by a high-performance Slingshot interconnect, with high-bandwidth device memory and a hierarchical memory/communication system supporting hybrid MPI+accelerator programming.

How it addresses lecture challenges: Uses accelerators for throughput-critical kernels while CPUs handle orchestration and complex tasks, leveraging fast interconnects and software stacks to scale across many nodes.

Observed strengths/limitations: Delivers exceptional performance for scalable, accelerator-friendly applications; challenges include porting/optimizing codes, managing data movement and heterogeneity, and achieving good scaling for communication- or irregularity-bound workloads (as reflected in public system/application reports).
