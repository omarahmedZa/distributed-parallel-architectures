1. Introduction to parallel computing

Why parallelism?

Single-core performance gains from higher clock frequency and deeper instruction-level tricks face physical limits: power density, heat, and diminishing returns from complexity. Parallel computing increases throughput and reduces time-to-solution by exploiting multiple processing elements simultaneously. The architectural question is never “parallelism or not?” in isolation—it is which form of parallelism, at what granularity, with what coordination and memory/communication costs.

Latencytime for one task/result
Throughputtasks/results per unit time
Overheadcoordination, communication, imbalance

Concurrency vs parallelism

Concurrency is a structuring/property of a system: multiple tasks make progress in overlapping time periods (e.g. by interleaving on one core). Parallelism is simultaneous execution on multiple hardware units. A concurrent program may run on one core; a parallel program requires multiple execution resources. Real systems combine both: concurrent tasks may be scheduled in parallel, and parallel execution introduces concurrency-control challenges.

Flynn’s taxonomy (basic view)

Flynn classified architectures by instruction and data streams:

ClassMeaningTypical intuition/examples
SISDSingle Instruction, Single DataClassic uniprocessor scalar execution.
SIMDSingle Instruction, Multiple DataVector units, many GPU lanes executing same operation on different elements.
MISDMultiple Instruction, Single DataRare in practice; sometimes discussed for fault-tolerant pipelines.
MIMDMultiple Instruction, Multiple DataMulticore CPUs, clusters, most general parallel/distributed systems.

Modern systems are hybrids (e.g. MIMD across cores/nodes with SIMD within cores). This taxonomy is a starting lens, refined in Lecture 1.

2. Shared-memory vs distributed-memory concepts

Memory model and address-space organization drive programming model, communication mechanisms, and scalability.

AspectShared memoryDistributed memory
Address spaceLogically common address space; threads/processes can access shared locations (subject to coherence/consistency rules).Private address spaces per node/process; data sharing via explicit messages.
CommunicationImplicit through loads/stores to shared data; synchronization primitives required.Explicit send/receive/collectives; programmer/runtime manages data movement.
Programming implicationsOften easier data sharing; must manage races, synchronization, and memory ordering.Clear ownership/locality; must partition data and orchestrate communication.
Scalability trade-offsHardware coherence/interconnect contention can limit scaling; NUMA effects emerge.Scales to many nodes; performance sensitive to latency, bandwidth, and communication/computation ratio.
Typical APIs/modelsThreads, OpenMP, shared-memory abstractions.MPI, PGAS variants, message-passing frameworks.
Design trade-off

Shared memory optimizes programmability for fine-grained sharing but pushes complexity into coherence, synchronization, and contention. Distributed memory optimizes explicit locality and scaling but pushes complexity into decomposition and communication. Hybrid systems (shared-memory nodes in a distributed cluster) are the norm in HPC.

3. Basic cache and memory hierarchy

Forward link: this section provides intuition used in Lecture 2 (Advanced Memory Architectures and Memory Hierarchy).

Locality and hierarchy levels

Processors are fast; large memory is comparatively slow. Systems bridge this gap with a memory hierarchy: small/fast levels close to the core (registers, L1/L2/L3 caches) backed by larger/slower levels (DRAM, remote memory, storage). Performance depends on locality:

  • Temporal locality: recently accessed data is likely reused soon.
  • Spatial locality: data near recently accessed addresses is likely accessed soon (cache lines/blocks).
Goal: keep working set in the fastest level that can hold it

High cache hit rates hide latency; misses expose memory/interconnect costs and can dominate runtime in bandwidth- or latency-bound kernels.

Coherence and consistency intuition (lead-in)

When multiple cores cache copies of shared data, updates create correctness questions:

  • Cache coherence: ensures a coherent view of a single memory location (e.g. writes become visible so cores do not indefinitely read stale copies) via protocols such as MSI/MESI/MOESI—detailed in Lecture 2.
  • Memory consistency: defines ordering guarantees for operations across different locations (what reorderings are allowed/observed), affecting synchronization and reasoning about parallel programs.

These mechanisms add hardware complexity and traffic (invalidations, directory lookups), creating scalability trade-offs explored in Lecture 2.

4. Basic MPI and OpenMP programming

Forward link: core concepts here are extended in Lecture 5 (Advanced Message Passing and Communication Mechanisms).

OpenMP (shared-memory parallelism)

OpenMP is a directive-based model for shared-memory systems (threads within a process/address space). It is well-suited to loop/data parallelism and incremental parallelization when data can be shared safely.

  • Core concepts: parallel regions, teams of threads, work sharing (#pragma omp parallel for), synchronization (barriers, critical/atomic), data scoping (shared/private).
  • Trade-offs: convenient for multicore nodes; requires care for races, false sharing, and NUMA locality.
// Minimal illustrative OpenMP (C/C++ pseudocode)
#pragma omp parallel for
for (int i = 0; i < N; i++) {
    a[i] = b[i] + c[i];
}

MPI (distributed-memory message passing)

MPI (Message Passing Interface) is the standard model for distributed-memory parallelism: processes with separate address spaces communicate explicitly.

  • Core concepts: processes/ranks, communicators, point-to-point send/receive, collectives (broadcast, reduce, gather/scatter), synchronization implied by communication patterns.
  • Trade-offs: explicit control and scalability across nodes; requires data partitioning and attention to communication overhead/latency.
// Minimal illustrative MPI (pseudocode)
MPI_Init(...);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);

if (rank == 0) {
    MPI_Send(buf, count, type, 1, tag, MPI_COMM_WORLD);
} else if (rank == 1) {
    MPI_Recv(buf, count, type, 0, tag, MPI_COMM_WORLD, &status);
}

MPI_Finalize();

ChooseGood fitWatch for

5. Basic speedup and efficiency calculations

Forward link: these fundamentals are deepened in Lecture 9 (Performance Modeling, Scalability and Optimization).

Definitions

  • Parallel time T(p): time with p processors/resources.
  • Speedup S(p) = T(1) / T(p): how much faster than the baseline.
  • Efficiency E(p) = S(p) / p = T(1) / (p · T(p)): fraction of resources usefully employed (0 < E ≤ 1 ideally, but overheads reduce it).
  • Cost C(p) = p · T(p): processor-time product. Cost-optimal if C(p) is on the order of T(1).
  • Overhead intuition T_o = p·T(p) - T(1): extra work/time from communication, synchronization, idle time/imbalance, and redundant computation.

Worked example 1 — speedup and efficiency

A kernel takes T(1)=100 s serially and T(8)=20 s on 8 cores.

QuantityCalculationResult
Speedup S(8)100 / 205×
Efficiency E(8)5 / 80.625 (62.5%)
Cost C(8)8 × 20160 processor-seconds
Overhead T_o160 − 10060 processor-seconds

Interpretation: useful speedup exists, but 37.5% of the available core-time is lost to overheads/imbalance/communication or limited parallel fraction.

Worked example 2 — effect of overhead

Suppose ideal parallel work would give T(4)=25 s for T(1)=100 s, but communication/synchronization adds 10 s: T(4)=35 s.

  • S(4)=100/35 ≈ 2.86× (not 4×), E(4)≈0.714.
  • Reducing overhead or improving overlap can recover performance—an architectural and algorithmic design concern (see Lectures 3, 5, 8, 9).
Fundamental HPC concepts

Performance depends on the balance of computation, memory bandwidth/latency, and communication; on parallel fraction and overheads; and on scalability (how performance changes with problem size and resources). Strong/weak scaling, Amdahl’s and Gustafson’s laws, and communication-to-computation ratio are formalized in Lecture 9.

Recap and check for understanding

  • Parallelism exploits multiple resources to improve time/throughput but introduces coordination, communication, and imbalance costs.
  • Shared vs distributed memory trade programmability/sharing against explicit communication and scaling behavior; hybrids dominate practice.
  • Locality and the memory hierarchy determine effective latency/bandwidth; coherence/consistency become central under sharing (Lecture 2).
  • OpenMP targets shared-memory parallelism; MPI targets distributed-memory message passing (Lecture 5 deepens communication mechanisms).
  • Speedup, efficiency, cost, and overhead quantify benefit and loss (Lecture 9 generalizes to scaling laws and modeling).
  1. If T(1)=120 s and T(6)=30 s, what are speedup and efficiency?
    Show answer

    S(6)=120/30=4×, E(6)=4/6≈0.667 (66.7%).

  2. Give one reason to prefer MPI over OpenMP, and one architectural cost that may limit MPI scaling.
    Show answer

    Prefer MPI for distributed nodes/private address spaces and explicit multi-node scaling. Scaling may be limited by network latency/bandwidth, synchronization, or communication-to-computation imbalance.

  3. Why does cache locality matter before studying coherence protocols in Lecture 2?
    Show answer

    Hierarchy/locality explains why caches exist and when accesses hit/miss; coherence protocols are needed because multiple caches may hold copies of shared data, creating correctness and traffic trade-offs.
