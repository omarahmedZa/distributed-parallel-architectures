Module 1 – Advanced Parallel Computer Architectures

Lecture 1 — Advanced Parallel Architecture Design

Understand how parallel architectures evolved and why modern designs favor multicore and many-core organizations; analyze architectural trade-offs and reason about performance and scalability implications.

Why this matters

Architectural design choices—how many cores, how capable each core is, how they share memory and interconnect—determine what workloads run efficiently, how systems scale, and where bottlenecks appear. This lecture frames the design space used throughout the course.

Prerequisites: Fundamentals (parallelism basics, Flynn’s taxonomy, memory models, speedup/efficiency intuition).

Learning objectives

  • Trace the evolution of parallel architectures and the forces (power, ILP limits, throughput demand) shaping them.
  • Compare multicore and many-core systems in organization, strengths, and limitations.
  • Evaluate architectural trade-offs (core complexity vs count, latency vs throughput, specialization vs generality).
  • Relate design decisions to performance and scalability outcomes.

Core ideas and mechanisms

Evolution of parallel architectures

Parallelism has been exploited at multiple levels: bit-level and instruction-level parallelism (ILP) within a core (pipelining, superscalar/out-of-order execution), data-level parallelism (SIMD/vector units), and thread/task-level parallelism across cores and nodes. As frequency scaling and ILP returns diminished under power/thermal constraints, designers shifted toward integrating multiple cores per die (multicore) and, for highly parallel workloads, many simpler throughput-oriented cores (many-core/accelerators). This evolution reflects a rebalancing: convert transistor budgets into parallel execution resources rather than ever-more-complex single-thread engines.

Multicore systems

Multicore processors integrate a modest number of relatively powerful cores (each with sophisticated pipelines, caches, predictors) sharing on-chip resources (last-level cache, memory controllers, interconnect). They target a mix of latency-sensitive and parallel workloads, preserving strong single-thread performance while enabling thread-level parallelism. Examples include general-purpose server/desktop CPUs with coherent shared memory.

  • Strengths: good serial/latency performance, mature programming models, flexible for diverse workloads.
  • Challenges: coherence/interconnect overheads, contention on shared caches/memory bandwidth, diminishing returns as core count grows.

Many-core systems

Many-core designs integrate a large number of simpler, highly threaded cores optimized for throughput and data parallelism (often with wide SIMD/SIMT execution). They excel when abundant parallelism hides latency and when memory access patterns can be structured for bandwidth.

  • Strengths: high aggregate throughput and energy efficiency for regular parallel workloads.
  • Challenges: weaker single-thread performance, sensitivity to divergence/irregularity, explicit data movement and locality management, programming complexity.

Performance and scalability

Performance depends on matching architecture to workload parallelism, locality, and synchronization/communication behavior (see Fundamentals). Scalability is constrained by serial fractions and overheads (formalized in Lecture 9), memory bandwidth, interconnect capacity, and coherence/coordination costs. A design that scales for throughput-oriented, regular workloads may not scale for latency-sensitive or communication-heavy ones.

Worked example: throughput vs latency orientation

Assume a workload with 90% parallelizable work. Using the basic speedup intuition from Fundamentals, ideal speedup is limited by the 10% serial portion; adding many simple cores yields large gains only if that parallel portion maps efficiently (high utilization, sufficient bandwidth, low divergence). A few powerful cores may finish latency-critical serial phases faster, improving end-to-end time despite lower peak parallel throughput. This illustrates why “more cores” is not uniformly better—the right balance is workload-dependent.

Limitations and scalability

  • Memory wall and bandwidth limits: data movement energy/latency increasingly dominate compute.
  • Coherence and interconnect scaling: maintaining shared-memory semantics at high core counts is costly (see Lectures 2 and 3).
  • Dark silicon/power constraints: not all transistors can be active at full speed simultaneously.
  • Programmability and portability: extracting performance across heterogeneous/many-core designs remains challenging.

Research problems

  • Heterogeneous and specialized architectures that balance latency, throughput, and energy.
  • Near-/in-memory processing and data-centric designs that reduce data movement.
  • Scalable coherence/interconnect mechanisms for high core counts.
  • Architecture–software co-design and portable performance across diverse parallel systems.

Recap and check for understanding

  • Parallel architecture evolution shifted emphasis from single-thread ILP/frequency to multicore and many-core parallelism.
  • Multicore favors latency/flexibility; many-core favors throughput for abundant parallelism—each with distinct bottlenecks.
  • Key trade-offs (core complexity/count, latency/throughput, sharing, specialization) drive performance and scalability.
  1. Why might a many-core processor underperform on a workload with frequent synchronization and irregular control flow?
    Show answer

    Simpler cores and throughput-oriented execution suffer from branch/thread divergence, synchronization/idleness, and poor utilization when parallelism is irregular or limited, while per-core latency is higher.

  2. Name one scalability limiter shared by large multicore designs.
    Show answer

    Examples: coherence traffic/directory overhead, shared-cache/interconnect contention, memory bandwidth saturation, or synchronization/serial bottlenecks.

Research Activities

Literature review — Paper 1

Citation M. D. Hill and M. R. Marty, “Amdahl’s Law in the Multicore Era,” Computer, vol. 41, no. 7, pp. 33–38, Jul. 2008. DOI: 10.1109/MC.2008.209.

Core contribution: Extends Amdahl’s-law reasoning to multicore chip design, modeling trade-offs between many simple cores, fewer powerful cores, and asymmetric (heterogeneous) multicore configurations under a fixed resource/budget constraint.

Method/architecture: Analytical models parameterized by chip resources, core performance, and parallel fraction to compare symmetric multicore, asymmetric multicore, and dynamic multicore organizations.

Key results: Shows that serial fractions severely limit symmetric many-core speedups and that asymmetric/dynamic designs can offer better speedups by accelerating serial/critical sections while still exploiting parallelism.

Limitations: High-level model abstracts away detailed microarchitectural effects, memory/interconnect behavior, and software/programmability challenges; real gains depend on mapping workloads to heterogeneous resources.

Literature review — Paper 2

Citation K. Olukotun, B. A. Nayfeh, L. Hammond, K. Wilson, and K. Chang, “The Case for a Single-Chip Multiprocessor,” in Proc. 7th Int’l Conf. Architectural Support for Programming Languages and Operating Systems (ASPLOS VII), 1996, pp. 2–11. DOI: 10.1145/237090.237140.

Core contribution: Argues that integrating multiple simpler processors on a single chip can deliver higher throughput and better implementation efficiency than a single wide-issue superscalar for workloads with thread-level parallelism.

Method/architecture: Compares a single-chip multiprocessor (CMP) organization against a complex superscalar design, analyzing implementation complexity and performance for parallel applications.

Key results: Demonstrates the attractiveness of CMPs for exploiting thread-level parallelism with simpler, more scalable hardware building blocks, influencing the industry shift to multicore processors.

Limitations: Benefits depend on availability of thread-level parallelism and effective parallel software; does not eliminate challenges of memory hierarchy, coherence, and programming complexity that arise in later large-scale multicore systems.

DimensionMulticore (few complex cores)Many-core (many simpler cores)

In practice, heterogeneous systems combine both to cover latency- and throughput-critical phases (see Lecture 10).

Case study — AMD EPYC multicore server processors

What it is: AMD EPYC is a family of server CPUs using a chiplet-based multicore design (multiple core dies coupled with I/O/memory interfaces) to deliver high core counts for data-center and HPC workloads.

Architectural design: Many general-purpose x86 cores organized in chiplets with shared cache hierarchies and multiple memory channels; design balances core count, cache/memory bandwidth, and I/O/interconnect capabilities within power envelopes.

How it addresses lecture challenges: Scales thread-level parallelism for server workloads while retaining strong per-core performance and a conventional shared-memory programming model; chiplet integration addresses manufacturing/scaling constraints of large monolithic dies.

Observed strengths/limitations: High throughput for parallel and multi-tenant workloads and strong memory/I/O capacity; however, performance can be limited by memory bandwidth/NUMA locality, shared-resource contention, and Amdahl’s-law effects on serial phases—illustrating core multicore trade-offs.
