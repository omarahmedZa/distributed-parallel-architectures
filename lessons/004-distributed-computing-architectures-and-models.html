Module 2 – Distributed Systems Architecture

Lecture 4 — Distributed Computing Architectures and Models

Compare distributed system architectures and models—client-server, peer-to-peer, cluster, and grid computing—and reason about distributed memory models and their design trade-offs.

Why this matters

Distributed architectures determine how computation, data, and control are placed across independent nodes. The right model improves scalability, availability, and cost-efficiency; the wrong one amplifies coordination, failure, and performance problems.

Prerequisites: Fundamentals (shared vs distributed memory, communication basics).

Learning objectives

  • Characterize core distributed system architectural styles and their assumptions.
  • Compare client-server and peer-to-peer models.
  • Differentiate cluster and grid computing in resources, management, and use cases.
  • Explain distributed memory models and implications for programming and performance.

Core ideas and mechanisms

Distributed system architectures

A distributed system comprises multiple autonomous nodes communicating over a network to provide a coherent service. Key architectural concerns include decomposition (services/components), communication (synchronous/asynchronous, RPC, messaging), state placement/replication, coordination, and failure handling. No single global clock or shared memory is assumed by default (see Lecture 6).

Client-server

Client-server separates requesters (clients) from providers (servers). Servers centralize resources/services; clients initiate interactions.

  • Advantages: clear roles, centralized control/security/policy, simpler consistency/management for shared state.
  • Limitations: server bottlenecks, single points of failure (without replication), scaling often requires careful partitioning/caching/load balancing.

Peer-to-peer (P2P)

P2P systems distribute roles among peers that can act as both clients and servers, often with decentralized resource sharing and lookup.

  • Advantages: resource aggregation, potential fault tolerance and scalability via decentralization, reduced central bottlenecks.
  • Limitations: complex discovery/routing, consistency and trust/security challenges, variable availability (churn).

Cluster computing

A cluster is a collection of tightly coupled, usually homogeneous nodes on a high-speed LAN, managed as a single system for performance/availability (e.g. HPC clusters, HA clusters). Resources are typically owned/administered within one organization with coordinated scheduling.

Grid computing

Grid computing federates geographically distributed, often heterogeneous resources across administrative domains to form virtual organizations. It emphasizes sharing, resource discovery, and cross-domain policies, typically over wider-area networks with higher heterogeneity/latency.

Distributed memory models

In distributed memory models, each process/node accesses local memory directly and exchanges data via messages (explicit) or higher-level abstractions (e.g. PGAS providing a global address view over partitioned memory). Implications: programmers reason about data distribution, locality, and communication; performance depends on minimizing and overlapping communication (see Fundamentals, Lecture 5).

Architectural design decisions and trade-offs

  • Centralization vs decentralization: simplicity/control vs scalability/fault isolation.
  • Consistency vs availability/latency: stronger coordination eases correctness but costs performance/availability under partitions (context for Lecture 6).
  • Coupling and heterogeneity: clusters offer predictability; grids/clouds offer flexibility at the cost of variability and management complexity.
  • State placement: replication improves availability/read scaling but complicates updates/consistency.

Limitations and scalability

  • Network latency/bandwidth and partial failures constrain coordination.
  • Heterogeneity and churn complicate scheduling and correctness.
  • Security and trust boundaries are first-class in multi-domain systems.

Research problems

  • Scalable coordination and consistency under geo-distribution and failures.
  • Resource management across heterogeneous, federated infrastructures.
  • Programming models that balance productivity, locality control, and portability.

Recap and check for understanding

  1. Give one advantage and one limitation of P2P compared to client-server.
    Show answer

    Advantage: decentralization can improve scalability/resource aggregation and reduce single bottlenecks. Limitation: harder discovery, coordination, consistency, and handling churn/security.

  2. How do clusters and grids typically differ in administration and environment?
    Show answer

    Clusters are usually single-admin, tightly coupled, and relatively homogeneous on fast LANs; grids federate heterogeneous resources across administrative domains over wider-area networks.

Research Activities

Literature review — Paper 1

Citation I. Stoica, R. Morris, D. Karger, M. F. Kaashoek, and H. Balakrishnan, “Chord: A Scalable Peer-to-peer Lookup Service for Internet Applications,” in Proc. ACM SIGCOMM, 2001, pp. 149–160. DOI: 10.1145/383059.383071.

Core contribution: Introduces Chord, a distributed lookup protocol that efficiently maps keys to nodes in dynamic P2P systems.

Method/architecture: Uses consistent hashing and a structured overlay (finger tables) so each node maintains limited state and lookups resolve in logarithmic hops with respect to the number of nodes.

Key results: Demonstrates scalable, decentralized lookup with provable efficiency and robustness properties under node joins/leaves (within model assumptions).

Limitations: Performance and correctness depend on overlay maintenance under churn; real deployments face latency variability, security/Sybil issues, and application-level consistency concerns.

Literature review — Paper 2

Citation I. Foster, C. Kesselman, and S. Tuecke, “The Anatomy of the Grid: Enabling Scalable Virtual Organizations,” Int’l Journal of High Performance Computing Applications, vol. 15, no. 3, pp. 200–222, 2001. DOI: 10.1177/109434200101500302.

Core contribution: Defines grid architecture principles centered on sharing resources across dynamic, multi-institutional virtual organizations with interoperable protocols.

Method/architecture: Articulates a layered hourglass-style architecture and requirements for resource sharing, security, and coordinated services across administrative domains.

Key results: Provides a conceptual and architectural foundation for grid middleware and federated resource management in distributed scientific computing.

Limitations: Cross-domain heterogeneity, policy, and performance variability complicate deployment; later cloud models addressed some operational issues with different trade-offs (centralized providers, virtualization).

Case study — SETI@home (volunteer distributed computing)

What it is: SETI@home was a large-scale volunteer computing project that distributed radio-signal analysis workloads to millions of participant machines over the Internet.

Architectural design: A centralized coordination/server infrastructure partitioned work units, distributed them to heterogeneous clients, and collected/validated results, leveraging otherwise idle consumer resources (a master–worker style at Internet scale).

How it addresses lecture challenges: Demonstrated massive aggregate throughput by exploiting distributed, loosely coupled resources and tolerating heterogeneity and intermittent availability through task granularity and redundancy/validation strategies.

Observed strengths/limitations: Achieved extraordinary scale and cost efficiency for embarrassingly parallel analysis; limitations included reliance on central coordination, variable/untrusted clients, limited suitability for tightly coupled communication, and challenges in verification and scheduling.
